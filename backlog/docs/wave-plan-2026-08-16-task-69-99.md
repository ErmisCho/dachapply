Execution plan for the 31 tasks filed by the 2026-08-16 discovery audit. A future session should

session-orchestrator agents dispatched in parallel waves, graded with the **asian-dad-eval** skill.

## Priority policy (owner's instruction, 2026-08-16)

1. **Me** — tasks that make the owner's own applying easier/faster
2. **Protect me** — personal exposure reduction
3. **Portfolio** — engineering quality worth showing in interviews
4. **Commercial** — multi-user / other-people features

Every wave below runs **without owner involvement**. Everything that needs the owner is in the
Owner Checklist at the bottom — it blocks nothing except the two ACs it names.

## Hard rules for the executing coordinator

- **TW-001**: Before dispatching a wave, write an asian-dad rubric for each task in it, derived
  only from the task's ACs, to `.claude/.asian-dad/task-<NN>-rubric.json` (gitignored). Never show
  rubrics to implementing agents. Rubric first, work second.
- **TW-002**: One agent per file territory. The entire frontend is ONE file
  (`frontend/src/App.tsx`), so **at most one agent per wave may edit App.tsx**. Backend crowds
  into `models.py`/`views.py`, so at most one backend agent per wave may edit those. This is why
  waves are pairs, not fans.
- **TW-003/004**: Coordinator re-verifies load-bearing claims and measures instead of asserting.
  Backend: `cd backend && uv run pytest -q` (hermetic). Frontend: `npx tsc --noEmit` && `npm test`.
  Responsive/a11y claims: same-origin iframe + `getBoundingClientRect()`; keyboard claims need an
  actual keyboard-only walkthrough. Subagents have no browser tools — the coordinator does browser
  verification itself.
- **TW-005**: A checked AC must be true. Where an AC depends on an Owner Checklist item, leave it
  unchecked and name the blocker.
- **TW-006**: Agents never commit/push/deploy. Coordinator stages individual files and commits.
  Deploys to production (push to main) are the owner's call.
- Tasks split across waves (backend half then frontend half) stay **In Progress** until both
  halves land and the coordinator has verified end to end. Never close on a half.

## Deviations from the plan as written

- **2026-08-16 — local `manage.py` commands hit production by default.** `backend/config/settings.py:21`
  loads the repo-root `.env` itself, and that file holds the production Neon `DATABASE_URL`. Clearing
  `DATABASE_URL` from the shell does **not** help (it was never in the shell), and `DB_NAME` is
  ignored whenever `DATABASE_URL` is set. During Wave 1 verification this caused `manage.py migrate`
  and a seed script to run against production Neon before it was caught; the accidental rows were
  removed with the owner's approval and the additive migration was left in place. Use
  `DATABASE_URL= DB_NAME=<scratch.sqlite3> uv run manage.py …` for anything local — an empty value
  beats `os.environ.setdefault` and forces the sqlite branch. Filed as TASK-100.
- **2026-08-16 — coordinator browser verification runs on its own stack.** The shared dev ports were
  already occupied by another session's servers pointing at production. Verification therefore runs
  its own backend on `:8010` against a scratch sqlite file and its own vite on `:5199`
  (`frontend/vite.verify.config.mjs`, untracked, deleted at the end of the run), driven by Playwright
  rather than the Chrome extension, whose cookie writes are blocked. The app session cookie is
  `app_sessionid`, not `sessionid` (see `config.middleware.SplitAdminSessionMiddleware`), and
  `/api/auth/csrf/` must be fetched once before any write.
- **2026-08-16 — TASK-82 was missing from every wave.** The plan schedules 30 of the 31 filed tasks
  and defers TASK-99 explicitly, but TASK-82 (cache the `/auth/me/` session check) appears in no
  wave and in no owner checklist item. It is a small `App.tsx`-only change, so the executing
  coordinator added it to **Wave 3 / ui-developer B**, the lightest App.tsx territory of the run.
