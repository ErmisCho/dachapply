## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
The board can only be sorted one way at a time, from a four-option `<select>` ("recommended", "fit
score", "newest", "feedback due"), and **status is not one of the options** — even though Status is a
column on the table and the pipeline stage is the thing the owner actually triages by.

Two things already exist and should be reused rather than rebuilt:

- `views.DEFAULT_BOARD_ORDERING` is *already* multi-key
  (`stale_rank, status_rank, priority_rank, -fit_score, -created_at`). Sorting by several keys is not
  a new capability in the queryset; it is simply not reachable by the user.
- `views.py:512` already annotates `status_rank`. **It is not pipeline order** — it is an *attention*
  order (`new`=0, `to_apply`=1, `reviewed`=2, `interview`/`offer`=3, `applied`=4, everything else=5).
  It deliberately collapses interview with offer and buries every closed status in one bucket, which
  is right for "recommended" and wrong for a user asking to sort by status. `JobLead.STATUSES` is
  already declared in pipeline order and is the correct source for that.

`BOARD_ORDERINGS` is a dict whose values are the real ordering tuples, so a raw query value never
reaches `order_by`. That property is deliberate and must survive this change.
<!-- SECTION:DESCRIPTION:END -->

## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
**Wire contract, fixed up front so the two halves can be built in parallel:**

    GET /api/jobs/?ordering=status,-fit_score

- comma-separated; optional `-` prefix per key for descending
- valid keys: `status`, `fit_score`, `priority`, `created_at`, `applied_at`, `updated_at`,
  `feedback_due_date` (each mapping to a real ordering expression server-side)
- at most 3 keys honoured; unknown or duplicate keys are dropped, not 400'd, so a stale bookmark
  degrades instead of breaking
- if nothing valid remains, fall back to `DEFAULT_BOARD_ORDERING`
- `-created_at` then `id` are always appended as final tiebreakers, so pagination cannot interleave

Keep `BOARD_ORDERINGS` as a lookup table: the query string selects *keys*, the server owns the
expressions. Ignoring unknown keys rather than erroring keeps that property trivially true.

**Do not use shift-click as the only way to add a second sort key.** This repo has now fixed that
exact class of defect twice — TASK-81 (hover-only disclosures) and TASK-102 (`display:none` controls
outside the tab order). A header button that cycles unsorted → ascending → descending → unsorted, and
appends to the existing sort when another column is already active, needs no modifier key and works
identically by keyboard, mouse and touch. Show precedence as a small number next to the arrow.

Status ordering must be built from `JobLead.STATUSES` (e.g. a `Case`/`When` generated by enumerating
it), so adding a status to the model cannot silently leave it unsorted. `status_rank` stays as it is
— "recommended" depends on it.

## Coordinator verification (2026-08-16)

Run against an isolated stack (scratch sqlite, backend on :8010, SPA on :5200), deliberately not the
`runserver` on :8000 that inherits the repo-root `.env`. Dataset built so the second sort key is what
decides: two rows per status, fit 30/90, priority set *against* fit so precedence is observable rather
than coincidental.

**AC1 — `?ordering=status`** returned, with each status contiguous:

    new, reviewed, to_apply, applied, interview, offer, accepted, rejected, withdrawn, skipped

`archived` is absent because `views.py:532` excludes it from the board by default; requesting
`?status=archived` returns its 2 rows, so all 11 statuses sort and one is merely hidden.

**AC2/AC3 — the second key genuinely breaks the ties**, and direction is per key:

    ordering=status,-fit_score   (new,90) (new,30) (reviewed,90) (reviewed,30) ...
    ordering=status,fit_score    (new,30) (new,90) (reviewed,30) (reviewed,90) ...
    ordering=status,-priority    (new,low,90)  (new,high,30)  ...
    ordering=status,priority     (new,high,30) (new,low,90)   ...

Swapping key order changes the result (`status,-fit_score` != `-fit_score,status`), so precedence is
real rather than nominal.

**AC4 — every hostile value fell back to the default**, by request rather than by reading the code:
`evaluations__job__created_by__password`, `-id`, `company`, `status; DROP TABLE jobradar_joblead;--`,
`../../etc/passwd`, `Fit_Score`, `?`. Mixed valid+junk still honours the valid key
(`nonsense,status` == `status`).

**AC5 —** identical requests returned identical order. **Adversarial check not in any AC:** a job
carrying more than one evaluation could duplicate under `order_by('evaluations__fit_score')` with
`.distinct()` — the classic join-ordering bug. 26 rows, 0 duplicated urls.

does not care what colour the text is. Only rendering it did.
