## Description

<!-- SECTION:DESCRIPTION:BEGIN -->
Reported 2026-09-23 with a screenshot: pasting a ChatGPT response into the dashboard prompt modal answered 'The server encountered an error. Please try again.'

Measured from the owner's actual payload rather than reproduced from a guess. Every scalar checked against its column:

    company                 len=  3   max=200   ok
    title                   len= 19   max=250   ok
    location                len=  6   max=200   ok
    source                  len= 92   max=120   ok
    salary_info             len=204   max=250   ok
    language_requirements   len=255   max=250   OVER by 5

views.import_eval (backend/jobradar/views.py:2167) calls import_any_json with no try/except, so the resulting Postgres DataError - value too long for type character varying(250) - escapes as a 500, and the client's generic fallback message is all the user sees.

Two things make this worse than a one-off:

1. The local runtime points at the production Postgres, which enforces length; sqlite does not. So the hermetic test suite cannot catch this class of bug, and neither can a local sqlite run. Any fix must not depend on the database raising.

2. The payloads come from a language model that is asked for job details in prose. language_requirements at 255 characters is not malformed - it is a reasonable answer to 'what are the language requirements'. salary_info at 204 is one clarifying sentence away from the same fate, and source at 92 of 120 is close. This will recur until the limits or the prompt change.

The generic client message is correct behaviour for a 500 and is not the bug; the 500 is.
<!-- SECTION:DESCRIPTION:END -->

## Owner decisions, 2026-09-23

**Widen the columns**, rather than refusing the import or truncating. The reasoning is that the
payload is generated by a language model asked for job details in prose, so a 255-character answer to
'what are the language requirements' is correct content in a column that is too narrow for it. A
clear 400 would be honest but would recur on every second import; truncation would silently lose the
end of a sentence that the CV prompt later reads as fact.

**Strip ChatGPT citation artifacts on import.** The same payload carried
':contentReference[oaicite:0]{index=0}' inside risk_notes even though the prompt already forbids
citations. Prompt wording alone did not hold, and these markers are never meaningful, so they are
removed server-side rather than left to reach a generated CV.

Consequence to respect when this ships: a migration reaches the production database the moment this
merges (scripts/start-container.sh runs migrate under set -e), and the owner's local runtime points at
that same database. Merge it at a moment the board is not in use, and verify the live health endpoint
afterwards.
