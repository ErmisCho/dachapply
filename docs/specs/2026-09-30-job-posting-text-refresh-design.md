# Job Posting Text Refresh — Design Spec

> Generated by /brainstorm on 2026-09-30. Status: approved.

## Problem

Job records can contain missing, stale, or irrelevant text even when their source URL still exposes the real vacancy. Users need a safe way to fetch that text, compare it with what is stored, correct either version, and explicitly choose the source used for CV and motivation-letter generation.

## Chosen Approach

Use a staged replacement: each job has one active source text and, when a fetch finds different text, one pending fetched candidate. Fetching never overwrites the active text. The user compares and edits both versions, then either accepts the fetched candidate or keeps the active version before generating documents.

A job-menu action fetches or refetches the posting immediately. Adding a job always saves the record; a successful fetch is retained as a pending candidate, while a failed fetch produces a per-listing warning and manual text field. When the signed-in user opens the application, a due background check runs unobtrusively for URL-backed jobs; its cadence is configured in Profile settings as Off, Daily, or Weekly, with Daily as the default.

The existing guarded server-side posting fetcher is reused. Background and manual checks compare normalized fetched text with active text: identical text requires no review, while different text becomes the single pending candidate. A later fetch may replace only that unaccepted candidate, never the active or manually corrected source.

## Trade-offs Accepted

| Trade-off | Rationale |
|-----------|-----------|
| Explicit review adds one decision before generation when fetched text differs | Prevents automatic destruction of manually corrected or historically accurate text. |
| Only one pending fetched candidate is retained | Avoids a version-history subsystem while preserving the only comparison the user needs. |
| Automatic checks run when the application opens rather than from a cloud scheduler | Delivers background repair without another worker or deployment schedule; checks resume on the next visit. |
| URL-backed jobs may be checked even when their active text appears valid | Comparing a fresh extraction is safer than guessing whether stored prose is a cookie notice or a real vacancy. |

## Acceptance Criteria (EARS)

### Ubiquitous (always-true invariants)
- The system shall keep active job text unchanged until the user explicitly saves an edit or accepts a pending fetched candidate.
- The system shall use only the accepted active text for CV and motivation-letter generation.
- The system shall permit the active and pending texts to be edited during the generation workflow.

### State-driven (While …)
- While a job has a pending fetched candidate, the generation workflow shall show editable active and fetched versions for comparison and require the user to choose “Keep current” or “Use fetched” before generation.
- While a job has no pending candidate, generation shall continue to use its active text without an extra decision.
- While automatic checking is Off, opening the application shall not fetch posting URLs automatically.

### Event-driven (When …)
- When a user selects “Fetch posting text” or “Refetch posting text” from a job menu, the system shall fetch the job URL and present differing text as a pending candidate without overwriting active text.
- When a job with a URL is added, the system shall save the job regardless of extraction success and attempt to retrieve its posting text.
- When add-time retrieval fails, the system shall show a per-listing warning and an editable manual text field.
- When add-time retrieval succeeds with text different from the saved text, the system shall retain the fetched text as the pending candidate and ask the user to compare it.
- When the application opens and the configured Off, Daily, or Weekly interval is due, the system shall check URL-backed jobs in the background and stage only differing results for review.
- When the user accepts an edited fetched candidate, the system shall make that text active and clear the pending candidate.
- When the user keeps an edited current version, the system shall save that version as active and clear the pending candidate.

### Optional feature (Where …)
- Where a job has no source URL, the system shall keep manual source-text entry available and shall not offer URL fetching.

### Unwanted behaviour (If … then …)
- If fetching fails, returns no readable vacancy text, or is rejected by the existing URL-safety checks, then the system shall preserve both active and pending text, report the failure honestly, and allow manual entry.
- If fetched and active text are equivalent after normalization, then the system shall record the successful check without creating a review candidate.

No open questions — all design decisions were resolved in the dialogue.

## Out of Scope

- A permanent history of every fetched or edited source-text version.
- A cloud scheduler that runs while the application is closed.
- JavaScript-rendered-page browser automation or a new scraping dependency.
- Automatic replacement of active or manually corrected source text.
