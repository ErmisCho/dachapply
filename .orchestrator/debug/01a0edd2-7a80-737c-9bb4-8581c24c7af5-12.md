### Hypothesized root cause
The review component stopped receiving pending-state fields from the compatibility-preserved PATCH response but did not set their resolved local values explicitly. · Confidence: high

## Phase 2 — Pattern

This is client cache drift across an API compatibility boundary. The persistence endpoint remains correct; every caller that owns optimistic/local job state must set derived pending fields itself after success.

## Phase 3 — Impact

Affected file: `frontend/src/App.tsx`. Dashboard keeps the wrong action label; Detail can keep the review panel and disable source/calibration controls after a successful decision. The single generator already sets `has_pending_source:false` in its own callback and is unaffected.

## Phase 4 — Solution

In `JobSourceReview.resolve()`, explicitly set `pending_source_text:''`, `pending_source_fetched_at:null`, and `has_pending_source:false` in the merged local job. Add a focused test assertion on that local resolved shape if it can be isolated without a DOM; otherwise pin the literal merge and re-run browser verification plus frontend/full gates.
