### Suspect commits

- `71b3049 Use the real job posting text in CV and letter generation, and link to the listing` — introduced the guarded fetcher and a read-only manual endpoint, deliberately requiring explicit adoption; it did not connect retrieval to task execution.
- `3de9740 Make generated applications job-specific and editable` — added popup source editing but retained the same worker flow.

### Instrumentation data

- API boundary: `generate_cv_documents` validates the request and calls `start_cv_task`; it never calls `fetch_posting_text`.
- Task boundary: `_run` reads the latest `JobLead`, then immediately calls `generate_cv_package`; static boundary count above confirms no fetch call exists between them.
- Fetch boundary: the only production caller of `fetch_posting_text` is `job_source_text_live`, a user-triggered read-only GET.
- Generation boundary: `generate_cv_package` reads `job.source_text` and accepts a meaningful `raw_description` fallback without attempting retrieval.
- Persistence boundary: `original_source_text` is the durable field and the cache already includes `job.source_text`, so saving before generation naturally invalidates fallback-based cache entries.

### Hypothesized root cause

The guarded posting fetch was exposed only as a manual read-only endpoint and never wired into the shared CV task worker before `generate_cv_package`. · Confidence: high

## Phase 2 — Pattern

This is a missing orchestration step, not a fetch/parser defect: TASK-237 built the retrieval primitive but intentionally stopped at explicit manual adoption. The same `_run` worker serves initial generation, recovered generation, batch starts, and revisions, so fixing individual API callers would leave sibling paths inconsistent. A regression test must execute `_run` and observe both persisted and generator-visible source text.

## Phase 3 — Impact

- `backend/jobradar/services/cv_tasks.py`: shared worker boundary where one retry can cover all model-backed CV/letter tasks.
- `backend/jobradar/tests/test_api.py`: existing direct `_run` tests avoid thread/database isolation and can verify success, skip, failure, and race-safe persistence.
- `backend/jobradar/services/posting_fetch.py`: reused unchanged; it already provides SSRF checks, redirect checks, timeout, size cap, extraction, and honest failure values.
- `backend/jobradar/views.py`: no change needed because all generation routes converge on `start_cv_task` / `_run`.

Risk: a user can save corrected source text while the network request is in flight. Persistence must use a compare-and-set condition so automatic retrieval never overwrites that newer value.

## Phase 4 — Solution

At the shared worker boundary, only when `original_source_text` is not meaningful and a URL exists, call the existing guarded fetcher once. On success, compare-and-set `original_source_text` against the value observed before the fetch, then refresh if another writer won; on failure, write nothing and continue with the existing honestly-labelled fallback. Add direct worker regressions for successful save/use, existing-source skip, failed-fetch fallback, and concurrent-edit preservation.

## Resolution

Added `_retry_missing_source` at the shared CV worker boundary. It performs one guarded fetch only when the durable original is missing, compare-and-set persists meaningful fetched text, refreshes before generation so a concurrent user save wins, and writes nothing on failure. Regression coverage executes the worker through success/save/use, existing-source skip, failed-fetch fallback, and concurrent-edit scenarios. Verification: 1,235 backend tests and 306 frontend tests passed; the production frontend build passed. The Backlog task records the implementation PR and merge commit.
