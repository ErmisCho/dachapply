# Debug session: groma React scan fails on unnamed frontend package
Created: 2026-09-25T15:31:21Z
Session: 01a0d927-2f6c-7542-844c-4a00b22d31be

## Phase 1 — Root Cause

### Error

```text
undefined is not an object (evaluating 'A.trim')
```

Exit code: 1. The compiled `groma` binary emitted no stack trace.

### Reproduction

```sh
groma scan
```

Environment: Windows x64; groma.md 0.5.0 GitHub release binary; `@groma/scanner-react@0.2.0`; Node v26.3.1. Frequency: always (2/2 in the working tree; 1/1 in a clean detached worktree with only the React scanner).

### Suspect commits

- `c28e0cd1` `TASK-503 - Qualify and improve the React scanner on public repositories` — the current React project model reads `manifest.name` as an assumed string and forwards it as the architecture root name.
- `a3eef4cc` `chore: release the include-list scanners as 0.2.0 for Groma 0.5.0` — released the affected scanner version used here.

### Instrumentation data

- Isolated scans in clean detached worktrees: TypeScript, Python, and JavaScript scanners pass; React alone fails with the exact error.
- `frontend/package.json` has no `name` property.
- Calling the installed React plugin's `scanReact` directly succeeds but returns this root without a name:

```json
{
  "id": "[\"frontend\",\"react-project\"]",
  "kind": "package",
  "file": "frontend/package.json"
}
```

- React scanner source types the parsed manifest as `{ name: string }` without runtime validation and passes `manifest.name` to the root record.
- In a clean detached worktree, adding `"name": "dachapply-frontend"` makes the same React scan pass and create four records.

### Hypothesized root cause

The React scanner forwards the absent optional `frontend/package.json` name as an undefined architecture-root name, which Groma core later treats as a string. · Confidence: high

## Phase 2 — Pattern

This is an unchecked external-manifest assumption at a plugin/core boundary. All inspected React fixtures contain package names, so a fixture with a valid private unnamed application package would have caught it. The other three configured scanners do not reproduce the failure; every unnamed React package can hit the same path.

## Phase 3 — Impact

Affected local file: `frontend/package.json`. External affected paths are `plugins/scanners/react/src/project.ts`, `plugins/scanners/react/src/scan.ts`, and the Groma core path that normalizes root names. Disabling React avoids the crash but loses React-specific callback and HTTP evidence; adding the package name preserves all recommended scanner coverage.

## Phase 4 — Solution

Add the existing lockfile package name `frontend` to `frontend/package.json`, then rerun scanner readiness, scan, and plain architecture view. No new test is needed in this application for static package metadata; the upstream scanner should add an unnamed-package fixture.

## Resolution

Added `"name":"frontend"` to `frontend/package.json`. `groma scanner check`, `groma scan`, `groma --plain view`, and `cd frontend && npm run build` pass. The setup generated `groma/` with all four recommended scanners pinned at 0.2.0. No commit was created because the working tree already contains unrelated user changes.
