# Debug session: Duplicate generation save controls
Created: 2026-10-01T10:00:00+02:00
Session: 01a0edd2-7a80-737c-9bb4-8581c24c7af5

## Phase 1 — Root Cause

### Error
```text
Authenticated browser observation after resolving a staged candidate in the single CV generator:

Company
Save company and job text
Company and job text saved.
Accepted job text (14881 characters). This is the text generation will use.
Current accepted text
Save job text
```
Expected one save action for company and job text; observed two save actions.

### Reproduction
1. Open a job's CV generator with a staged candidate.
2. Edit current text and choose “Keep current”.
3. Observe the no-pending state after persistence.

Environment: visible Chrome over CDP, Vite frontend, local Django/SQLite backend.
Frequency: always.

### Suspect commits
- Uncommitted TASK-255 integration fix added a standalone “Save company and job text” button after the full suite exposed the old raw-source assertion.

### Instrumentation data
- `PostingSource` already renders a no-pending `Save job text` branch whenever `onResolve` is supplied.
- The single generator supplies `onResolve={saveGenerationJob}`, so it already retained a working persistence action after the shared-component move.
- The newly added standalone button invokes the same function and is therefore duplicate behavior, not a separate capability.
- Batch generation also supplies `onResolve` with no pending candidate, exposing an unnecessary save action against a read-only accepted pane.

### Hypothesized root cause
The integration fix overlooked `PostingSource`'s existing no-pending resolution branch and added a second control for the same persistence path. · Confidence: high

## Phase 2 — Pattern

This is duplicate UI created during shared-component consolidation. The reusable component already owns source-resolution actions; callers should configure its label/presence rather than add sibling controls.

## Phase 3 — Impact

Affected file: `frontend/src/App.tsx`; contract test: `frontend/src/cvPopup.test.tsx`. The single generator needs one context-specific label because the same PATCH saves company and source. Batch generation needs resolution controls only while a candidate exists.

## Phase 4 — Solution

Remove the standalone button. Add an optional no-pending save label to `PostingSource`, pass “Save company and job text” from the single generator, and only provide the batch resolution callback when a candidate exists. Update the focused raw-source assertion and re-run focused tests/build plus the browser flow.

## Resolution

Uncommitted TASK-255 working tree. Removed the duplicate caller button, configured the shared control's single-generator label, and hid no-op batch save controls when no candidate exists. Verification: 27 focused frontend tests passed, production build passed, and `git diff --check` passed.
