# Debug session: Local browser login cache table
Created: 2026-10-01T09:45:00+02:00
Session: 01a0edd2-7a80-737c-9bb4-8581c24c7af5

## Phase 1 — Root Cause

### Error
```text
Internal Server Error: /api/auth/login/
sqlite3.OperationalError: no such table: dachapply_cache
...
django.db.utils.OperationalError: no such table: dachapply_cache
POST /api/auth/login/ HTTP/1.1 500
```
Process outcome: browser remained on `/login` and showed “The server encountered an error.”

### Reproduction
```bash
DATABASE_URL='' DB_NAME=<fresh-browser.sqlite3> DEBUG=1 uv run python manage.py migrate --noinput
DATABASE_URL='' DB_NAME=<fresh-browser.sqlite3> DEBUG=1 uv run python manage.py runserver 127.0.0.1:8000 --noreload
# Submit local test-user login in the browser.
```
Environment: fresh local SQLite browser-verification database, Django development server, Vite frontend.
Frequency: always on this fresh database.

### Suspect commits
- None. Django migrations do not create the configured database-cache table; it is managed by Django's separate `createcachetable` command.

### Instrumentation data
- Application migrations and local test-user seeding succeeded.
- The login request reaches DRF throttling before authentication.
- DRF's throttle cache executes `SELECT ... FROM dachapply_cache`, and the fresh database lacks that table.
- The repository's test settings use an in-memory cache path, so the full automated suite does not expose this browser-harness setup requirement.

### Hypothesized root cause
The fresh browser-verification SQLite database was migrated but its separately managed Django database-cache table was not created. · Confidence: high

## Phase 2 — Pattern

This is local harness setup, not an application regression. Django's database cache backend requires `manage.py createcachetable` in addition to migrations.

## Phase 3 — Impact

Only the disposable browser-verification database is affected. No repository code or production data needs modification.

## Phase 4 — Solution

Run `manage.py createcachetable`, then retry login and continue browser verification.

## Resolution

Ran `manage.py createcachetable` against the disposable browser database. Login then succeeded and the authenticated board loaded; no repository code changed.
