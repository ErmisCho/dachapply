# Debug session: localhost port 8000 root returns Django 404
Created: 2026-08-30T14:11:36Z
Session: task-205-2026-08-30-bugfix-1

## Phase 1 — Root Cause

### Error

Exact response from the reported URL:

```text
GET http://127.0.0.1:8000/
HTTP/1.1 404 Not Found
Content-Type: text/html; charset=utf-8

<title>Page not found at /</title>
<h1>Page not found <small>(404)</small></h1>
The empty path
```

The Django DEBUG page lists only `admin`, `admin/`, `api/`, and `^static/(?P<path>.*)$`; the empty path matches none of them. HTTP requests have no process exit code.

### Reproduction

```bash
curl -sS -D - http://127.0.0.1:8000/
```

Environment: Windows, released runtime commit `284c470`, Django development server on `127.0.0.1:8000`, Vite development server on `127.0.0.1:5173`, `DEBUG=True`. Frequency: always while `frontend/dist` is absent.

### Suspect commits

- `ab523e7 fix(dev): sync localhost to released main` — introduced the disposable runtime that runs `npm ci` followed by `npm run dev`, but does not create `frontend/dist`.
- The existing conditional SPA URL configuration predates that launcher and only installs the frontend catch-all when `FRONTEND_DIST.exists()`.

### Instrumentation data

- Boundary, browser → Django: `GET http://127.0.0.1:8000/` returns 404 with the empty-path diagnostic.
- Boundary, browser → Vite: `GET http://127.0.0.1:5173/` returns 200 and the frontend HTML (`Content-Length: 678`).
- Runtime filesystem: `C:/Users/Administrator/AppData/Local/dachapply/main-runtime/frontend/dist` is absent.
- Runtime settings (loaded with the existing one-command production-DB guard opt-in and no database query): `DEBUG=True`, `FRONTEND_DIST_EXISTS=False`, `FRONTEND_URL=http://localhost:5173`.
- Runtime URL patterns are exactly `admin`, `admin/`, `api/`, and `^static/(?P<path>.*)$`.
- `scripts/dachapply-local-runtime.cmd` starts Django on port 8000 and `npm run dev` on port 5173 after `npm ci`; it never runs `npm run build`.
- `backend/config/urls.py` installs the SPA catch-all only inside `if settings.FRONTEND_DIST.exists()` and has no missing-dist local root route.
- `README.md` identifies `http://localhost:5173` as the normal local app and port 8000 as the Django/admin server.

### Hypothesized root cause

The released local launcher intentionally serves the frontend through Vite without building `frontend/dist`, while Django registers its root/catch-all route only when that absent directory exists. · Confidence: high

## Phase 2 — Pattern

This is a dev-server integration gap, not a Django DEBUG configuration defect. Production builds `frontend/dist`, so the existing SPA catch-all remains valid there. The repository has no root-routing regression test; existing launcher coverage verifies release synchronization and process startup only. Search found no earlier root-redirect fix.

## Phase 3 — Impact

Affected:

- `backend/config/urls.py`: missing-dist DEBUG routing.
- Backend URL regression coverage: must prove the local root redirects while preserving the existing API/admin/static and built-SPA branches.

Not affected:

- API and admin routes precede any frontend fallback.
- Vite itself is healthy on port 5173.
- Production routing has a built frontend and must continue serving `index.html` directly.
- Database selection, local launcher synchronization, active development worktrees, and Azure deployment semantics require no change.

## Phase 4 — Solution

When `DEBUG=True` and `FRONTEND_DIST` is absent, add only an exact empty-path temporary redirect to `settings.FRONTEND_URL`. Keep the existing built-SPA catch-all unchanged. Add a focused Django URL test that reloads the URLconf under an explicitly missing temporary dist path, checks the 302 location, then restores and reloads the original URLconf to avoid cross-test state.

## Resolution

Added an exact empty-path temporary redirect to `settings.FRONTEND_URL` only when DEBUG is enabled and `FRONTEND_DIST` is absent. Added focused URLconf regression coverage. Verification passed: 1028 backend tests, 195 frontend tests, production build, Django checks, compileall, npm audit, and a migrated alternate-port HTTP run that returned 302 to `http://localhost:5173` and followed to DACHApply with HTTP 200.
