### Suspect commits
- The failure comes from the newly added uncommitted regression test, not a production commit.
- The test assigns `job.original_source_text` and calls `job.save(update_fields=...)`, but `JobLead.save()` deliberately restores any already meaningful persisted original source before saving.

### Instrumentation data
- The `job` fixture is created with meaningful `original_source_text=SUMMARY`.
- `JobLead.save()` queries the existing value and executes `self.original_source_text=existing` whenever it is meaningful.
- Therefore the test's attempted accepted-text replacement never reaches the database; due refresh correctly compares the fetched posting against `SUMMARY` and reports `staged: 1`.
- Existing tests that deliberately arrange a changed original source use `JobLead.objects.filter(pk=...).update(...)`, confirming the intended test setup pattern.
- `posting_fetch.extract_text(POSTING_HTML)` and the fetch path both use the same extractor; there is no extraction mismatch.

### Hypothesized root cause
The test tried to bypass the model's intentional accepted-source immutability through `save()`, so its database fixture never became identical to the fetched posting. · Confidence: high

## Phase 2 — Pattern

This is a test-fixture setup error caused by a load-bearing model invariant. Repository search finds established direct-query setup in `test_api.py` whenever tests need to simulate already persisted source text. No production path incorrectly mutates accepted text.

## Phase 3 — Impact

Only `backend/jobradar/tests/test_posting_fetch.py` is affected. Replacing fixture setup with a queryset update exercises the intended identical branch without weakening the model invariant. The failure-path half must use the same setup mechanism for its second source replacement.

## Phase 4 — Solution

Use `JobLead.objects.filter(pk=job.pk).update(...)` for both explicit database arrangements, then refresh the instance before the due request. Re-run the focused posting-fetch suite.
