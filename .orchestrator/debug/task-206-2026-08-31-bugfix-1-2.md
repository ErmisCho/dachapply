## Phase 1 — Root Cause

### Error

The owner-provided screenshot `pi-clipboard-9ff8d63c-7f10-4b9d-ad3d-d80319d7956f.png` shows one Email decisions card with:

```text
Clear the waiting-for-feedback clock
Set status to rejected
Drafted reply (in Gmail Drafts): continued-interest wording
```

The owner reports that the recruiter had already personally closed the conversation and the owner had already replied goodbye. This is a semantic runtime defect, so there is no stack trace or process exit code.

### Reproduction

1. Capture a matched recruiter message whose polite closure language lacks the existing exact rejection phrases.

3. Generate/retrieve the message’s template draft and render the job’s pending email decisions.
4. Observe that the closure is stored as `recruiter_reply`, the generic recruiter template states continued interest, and the panel renders that draft despite the owner’s newer reply.

Environment: released main/runtime `ad4ef3f`; production metadata read through the existing owner-scoped database with the scheduler disabled. No Gmail endpoint was contacted. Frequency: always for the measured stored chronology.

### Instrumentation data

- One incoming formal rejection and one personal closure arrived seven minutes apart for the same tracked job.
- The personal closure was stored as `recruiter_reply`; `_DRAFT_WORTHY_CLASSIFICATIONS` therefore admitted it.
- `_template_polite_follow_up()` does not inspect the message body and always emits continued-interest wording for every `recruiter_reply`.
- The owner’s genuine same-thread reply arrived 52 minutes after the personal closure.
- The app-created Gmail draft was recorded about 31 hours after that owner reply, with `sent_at` still null.
- A second owner-looking row is the Gmail draft itself: its `gmail_id` equals the stored draft message id, so any chronology guard must exclude that self-capture rather than treating every app-created draft as proof the owner replied.
- `maybe_draft_reply()` checks classification, job status, bulk markers, and duplicate undecided drafts, but never checks for a newer same-thread owner message.
- `JobMailboxConversationCard` selects the first written draft from suggestion-linked messages/full history and ignores both draft chronology and `sent_at`.
- Existing sent reconciliation requires draft disappearance and an owner message newer than `draft.created_at`; the genuine reply here is older than the late-created draft, so that intentionally conservative send proof does not apply.

### Hypothesized root cause

A closure message can remain `recruiter_reply`, whose body-agnostic fallback generates continued-interest text, while both draft creation and rendering ignore an already-captured newer owner reply in the same thread. · Confidence: high

## Phase 2 — Pattern

This is stale-action context loss across classification, generation, and presentation. The classifier’s narrow phrase list misses a polite terminal variant; the generator treats the broad fallback class as one intent; and the UI treats “written” as synonymous with “still actionable.” A focused regression must cover all three boundaries, including exclusion of the app draft’s own captured Gmail message id.

## Phase 4 — Solution

1. Recognize the measured, specific polite-closure phrase as a strong rejection signal rather than broadening to vague words such as “best wishes.”
2. Refuse draft generation when a newer genuine owner-authored message is already captured in the same nonblank thread, excluding a row whose Gmail id is the draft’s own Gmail message id.
3. Expose a bounded `stale_reason` only on action-oriented mailbox serializers; render a neutral stale-draft notice/link instead of the contradictory body/edit/chat controls.
4. Preserve current drafts when no later owner response or terminal outcome exists, and verify no-send/no-Gmail behavior.

## Resolution

Implemented three bounded protections: the specific polite-closure phrase now classifies as rejection; draft generation refuses a captured or same-batch newer owner reply in the same thread; action serializers expose a stale reason that makes the UI replace old body/edit/chat controls with a non-destructive notice and exact Gmail-draft link. The app draft’s own captured Gmail message id is excluded from owner-reply proof.
