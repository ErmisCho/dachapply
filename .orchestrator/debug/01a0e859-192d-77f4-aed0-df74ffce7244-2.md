## Phase 1 — Root Cause

### Error
No exception is raised. The deterministic reproduction exits 0 and prints the same output names for two distinct jobs:

```text
('Doe-Jane-CV-Acme-Engineer.tex', 'Doe-Jane-Letter-Acme-Engineer.tex')
('Doe-Jane-CV-Acme-Engineer.tex', 'Doe-Jane-Letter-Acme-Engineer.tex')
```

A second reproduction with that CV already present exits 0 and prints:

```text
Doe-Jane-CV-Acme-Engineer-2.tex
```

### Reproduction
```bash
cd backend
uv run python manage.py shell -c "from types import SimpleNamespace; from jobradar.services.cv_generator import _target_names; a=SimpleNamespace(id=1,company='ACME',title='Engineer'); b=SimpleNamespace(id=2,company='ACME',title='Engineer'); print(_target_names(a,'Doe-Jane')); print(_target_names(b,'Doe-Jane'))"
uv run python manage.py shell -c "from pathlib import Path; from tempfile import TemporaryDirectory; from jobradar.services.cv_generator import _unique_destination; t=TemporaryDirectory(); d=Path(t.name); (d/'Doe-Jane-CV-Acme-Engineer.tex').write_text('existing'); print(_unique_destination(d,'Doe-Jane-CV-Acme-Engineer.tex').name)"
```
Environment: Windows, CPython 3.13.5, Django project shell. Frequency: always.

### Suspect commits
- `ae3595a` Confirm repeat CV generation and restore TeX copy — added client confirmation but deliberately did not change the persistence collision policy.
- Existing `_target_names` and `_unique_destination` behavior predates the recent popup work; no recent commit introduced the ambiguity.

### Instrumentation data
- `_target_names` receives the full job but reads only `company` and `title`; `job.id` is ignored.
- Both job IDs therefore produce byte-identical CV and generic `Letter` names.
- `latest_generated_sources` searches those ambiguous stems and numbered variants.
- `persist_generated_files` calls `_unique_destination` on every fresh generation, so confirmation is followed by a new `-2` path rather than replacement.
- The generation popup has no editable company/source state; it only renders `PostingSource` from the preview.
- The existing `source-text` PATCH route is already scoped through `get_object()` and validates meaningful source text, so it is the narrow existing write boundary to reuse.

### Hypothesized root cause
Generated output identity is derived from mutable company/title text and fresh persistence always requests a unique path, so distinct jobs collide while confirmed repeats are forced into numbered copies. · Confidence: high

## Phase 2 — Pattern

This is an identity-versus-display-name bug: a human-readable slug is being used as the stable key. `_target_names` has one production caller in fresh package generation plus lookup/reporting callers; `latest_generated_sources` is shared by preview, readjustment, recompilation, and copy restoration. A regression test should use two jobs with equal company/title but different IDs, and another should persist twice with explicit replacement and assert the same paths and no numbered files.

## Phase 3 — Impact

Affected code and dependents:
- `backend/jobradar/services/cv_generator.py`: naming, lookup, persistence target selection, package generation.
- `backend/jobradar/services/cv_tasks.py`: fresh-task replacement intent must reach package generation.
- `backend/jobradar/views.py`: generation confirmation enforcement and atomic company/source save.
- `frontend/src/cvModel.ts`: selected-template existing-output detection and unknown-company predicate.
- `frontend/src/App.tsx`: confirmation payload and editable popup fields.
- Backend/frontend regression tests for all paths above.

Legacy generic `Letter` names must stay in lookup candidates, but new files need a job-ID-bearing stem and the selected letter asset label/key.

## Phase 4 — Solution

Use the job ID in all new output stems, derive the letter segment from the selected template label/key, retain exact legacy candidates for lookup, expose selected letter artifacts in preview, require explicit replacement intent at the generation endpoint, and overwrite only the selected job/template paths after confirmation. Extend the existing source-text PATCH action to validate and save an optional company in the same database update; use that route from editable popup controls and disable generation while edits are unsaved.

Tests identified:
- Distinct job IDs with identical company/title generate and discover distinct paths.
- Letter output uses `Anschreiben`; legacy `Letter` remains discoverable.
- Unconfirmed existing output is rejected; confirmed generation receives replacement intent and persistence updates the same path without `-2`.
- Frontend selected-template detection, cancel-before-request, replacement payload, unknown-company warning, and popup save wiring.

Hypothesized root cause: Existing test doubles encoded the old generic `Letter` filename and exact call shape rather than document role, while the route needlessly widened unchanged calls with `replace_existing=False`. · Confidence: high

Minimal correction: make route lookup doubles accept the optional letter key, classify synthetic PDF page counts by the stable `-CV-` marker, only pass `replace_existing` when true, and include the intentional `letter_template` artifact metadata in the exact-key assertion (the client needs it to stop a completed task for one template from masquerading as another).
