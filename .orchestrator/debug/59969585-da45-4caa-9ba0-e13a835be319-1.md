### Suspect commits

- No committed change introduced this polling failure: the branch production diff only changes `cv_generator.py` and `test_local_provider.py`.
- `cv_tasks.py` already calls `close_old_connections()` in its background worker before and after long generation, showing that long model waits can outlive pooled DB connections.

### Instrumentation data

- Preview request: HTTP 200, generator configured.
- Generation start: HTTP 202, task `d073e5043bd34da39a2587dd1f39175e`.
- In-memory task advanced from Queued to Generating CV, then Repairing 1/2, then Repairing 2/2 over 84 seconds.
- The exception occurred in `UsageTrackingMiddleware.record_usage` before `cv_generation_status` ran; no status-view or model-response code appears in the stack.
- `lms ps --json` after the shell exited showed the model idle, so the HTTP inference request had ended.
- The shell exception terminated the process that owned the daemon generation thread and its in-memory task, preventing a final result from being observed.

### Hypothesized root cause

The verification harness reused a remote PostgreSQL connection after an 84-second model wait and failed in request middleware before reaching the in-memory status view. · Confidence: high

## Phase 2 — Pattern

This is the known long-running-model/pooled-DB-connection class already handled inside `cv_tasks._run` with `close_old_connections()`. The ad-hoc same-process APIClient polling harness introduced a separate DB query on every poll through usage middleware. No production request path or changed model code caused the exception.

A product regression test is not warranted: the concrete failure belongs to the ad-hoc verification harness, while production requests use separate request lifecycles. The existing suite already covers background-worker connection recycling.

## Phase 3 — Impact

- Failed component: temporary verification command only.
- Production files implicated by stack: `backend/jobradar/middleware.py`, but changing it would be out of TASK-221 scope and would treat a harness artifact as a product bug.
- TASK-221 files remain `backend/jobradar/services/cv_generator.py` and `backend/jobradar/tests/test_local_provider.py`.
- The real CV run must be repeated because the shell process died before the daemon thread could report completion.

## Phase 4 — Solution

Do not change application code. Repeat the real CV run through `start_cv_task`, but poll `get_cv_task` directly in the same process; this reads the task's in-memory lock-protected dictionary and performs no database query or usage-middleware work. The background worker retains its own existing `close_old_connections()` boundaries.
