# Debug session: successful HTTP verification shell exits 1 during cleanup
Created: 2026-08-30T14:27:00Z
Session: task-205-2026-08-30-bugfix-2

## Phase 1 — Root Cause

### Error

The verification produced all expected application results:

```text
HTTP/1.1 302 Found
Location: http://localhost:5173
follow=200 http://localhost:5173/ title=<title>DACHApply
```

but the shell command exited 1. After the EXIT trap, port 8010 had no listener but the disposable `backend/db.sqlite3` still existed.

### Reproduction

Run the migrated alternate-port verification with an EXIT trap that kills the background wrapper/listener and immediately removes `backend/db.sqlite3`. Application assertions pass, then the shell returns 1 during immediate teardown.

Environment: Windows, Git Bash background `uv run python manage.py runserver`, disposable SQLite file. Frequency: observed once in one attempt.

### Suspect commits

- No repository commit. The failure is in the one-off shell cleanup timing.

### Instrumentation data

- Runserver log contains three successful `GET /` responses, each `302 0`; there is no application error.
- Captured redirect and followed response match the expected status, Location, effective URL, and DACHApply title.
- After cleanup, `Get-NetTCPConnection -LocalPort 8010 -State Listen` reports `listener=none`.
- A subsequent process scan finds no process whose command line references `task-205-local-root` except the scan command itself.
- The SQLite file still existed immediately after teardown, showing the immediate removal step did not complete while the background process tree was winding down.
- Independent checks of the Location grep and final string comparison return 0.

### Hypothesized root cause

The Windows background runserver process released its listener before fully releasing the disposable SQLite file, so the EXIT trap’s immediate file removal failed and became the command’s exit status. · Confidence: medium

## Phase 2 — Pattern

This is a Windows process-teardown race in an ad hoc verification script. It does not contradict the measured HTTP behavior. Cleanup should wait for process exit/file release and verify deletion separately rather than combining application assertions and teardown into one exit status.

## Phase 3 — Impact

Affected only: ignored `backend/db.sqlite3` in the isolated worktree and the wrapper command’s reported exit code. Port 8010 is closed, no task process remains, and production/application files are unaffected.

## Phase 4 — Solution

Delete the now-unlocked disposable SQLite file in a separate command, verify absence, and record the already captured HTTP results as the application proof. Do not modify product code for a teardown race.

## Resolution

After the process tree finished, removed the disposable SQLite file in a separate command and verified both file absence and no listener on port 8010 (`cleanup=pass`). The captured application proof remains 302 → `http://localhost:5173` → 200 DACHApply.
