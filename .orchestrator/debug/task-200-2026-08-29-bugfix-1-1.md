# Debug session: job board traps edge-crossing wheel movement
Created: 2026-08-30T06:41:00Z
Session: task-200-2026-08-29-bugfix-1

## Phase 1 — Root Cause

### Error
User report: `if the job listings scrollbar reached its limit and user scrolls even more towards the maximum scrolled direction, the main scrollbar should get activated`.

Measured released behavior: one 180 px downward wheel input starting 50 px before the board bottom produced `boardDelta=50`, `pageDelta=0`, and `lostDelta=130`.

### Reproduction
Headless Chrome against `http://localhost:5173/` at 1440×900, logged into the synthetic demo account. Add a DOM-only 1800 px fixture inside `.job-table-scroll`, place `scrollTop` at `max-50`, keep the pointer over the board, and issue one `page.mouse.wheel({deltaY:180})`.

Environment: Chrome; desktop `@media (min-width:1024px)` board with `max-height:calc(100vh - 7rem); overflow-y:auto`. Frequency: always for an input that crosses the board edge.

### Suspect commits
- `00ab936 fix(board): stop the sticky table header covering the first job row` — introduced the bounded internal scroller needed for the sticky header; not a mistake, but the point at which scroll handoff became relevant.
- Current main `d2c3237` — no wheel handler or non-default overscroll rule exists.

### Instrumentation data
- Wrapper: `.job-table-scroll`; `scrollTop=1497`, `max=1547` before input.
- Input: `deltaY=180`, pointer remained inside the board.
- After input: `scrollTop=1547`, page `scrollY` unchanged.
- A discrete input beginning at the exact edge chains natively; an edge-crossing input loses its remainder, explaining the required extra gesture.

### Hypothesized root cause
Chrome applies an edge-crossing wheel input only to the nested board's remaining range and discards the unconsumed delta instead of transferring that remainder to the page. · Confidence: high

## Phase 2 — Pattern

This is nested-scroll delta loss, not `overscroll-behavior:contain`: the wrapper uses the browser default and has no wheel handler. Other overflow areas are dialogs or message bodies and do not represent the home-page board requested here.

## Phase 3 — Impact

Affected files: `frontend/src/App.tsx` and one focused frontend test. The desktop board must retain its bounded vertical and horizontal scrolling, sticky header, and portalled popups. Mobile has no internal vertical board scroll and must remain unchanged.

## Phase 4 — Solution

For desktop wheel events only, compute how much of the input fits in the board's remaining range. Let fully consumable inputs use native scrolling. When an input crosses or starts at an edge, prevent the native event, apply the board portion, and scroll the page by the remainder. Verify middle, top, bottom, and crossing deltas in tests and Chrome.

## Resolution

Added one non-passive wheel listener to the existing desktop board wrapper. It lets fully consumable inputs use native scrolling, but splits edge-crossing inputs between the board's remaining range and `window.scrollBy`. Focused tests passed. Headless Chrome measured: middle `180/0`, bottom crossing `50/130`, bottom `0/180`, top crossing `-30/-150`, and top `0/-180` as board/page deltas.
