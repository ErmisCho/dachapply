# Debug session: direct Gmail conversation and deployed manual mailbox run
Created: 2026-08-29T16:31:00Z
Session: task-198-2026-08-29-feature-1

## Phase 1 — Root Cause

### Error
User report (verbatim): `this link doens't open the acutal email`.
Observed result in the supplied screenshot: Gmail opens `#search/rfc822msgid:...` and renders a one-row search-results page rather than the conversation.
No exception or non-zero process exit occurs; this is wrong navigation behavior.

The second symptom is that the deployed app offers no visible manual mailbox control even though `POST /api/mailbox-runs/run-now/` supports the deployment's no-credentials queue path.

### Reproduction

```bash
cd backend && uv run pytest -q jobradar/tests/test_mailbox.py::test_gmail_conversation_url_strips_angle_brackets_and_url_encodes jobradar/tests/test_mailbox_panel.py::test_job_mailbox_endpoint_message_gmail_url_is_built_from_the_message_id
# current assertions prove the emitted URL is https://mail.google.com/mail/u/0/#search/rfc822msgid:...

git blame -L 600,603 -- frontend/src/App.tsx
# line 602 is `{owner&&status?.has_credentials&&<section ...>`, so status.has_credentials=false removes the control.
```

Environment: Windows, Python via `uv`, Node 26.3.1, branch `worktree-mailbox-links-manual-run`, baseline `8a5f049`.
Frequency: always for stored-message links; always on the deployed backend where `/api/mailbox-runs/status/` reports `has_credentials: false`.

### Suspect commits
- `5611529` / earlier TASK-121 implementation — the shared builder intentionally chose an RFC822 Gmail search URL even though `MailboxMessage.thread_id` is persisted and exposed.
- `fb4a51b` `feat(mailbox): review uncertain mail with local Codex` — changed the run-control render condition from `owner` to `owner && status.has_credentials`, regressing TASK-124's supported deployed queue path.

### Instrumentation data
- Storage boundary: `MailboxMessage` has both `message_id` and Gmail `thread_id`; production history was backfilled specifically so conversations can be addressed by `thread_id`.
- Serialization boundary: `MailboxMessageSerializer.get_gmail_url()` passes only `obj.message_id` to `_gmail_url`; `obj.thread_id` is ignored.
- URL boundary: `gmail_conversation_url()` emits `#search/rfc822msgid:<message-id>` for every non-draft message.
- Client boundary: all message action links render the server-provided `m.gmail_url` unchanged, so the client is not rewriting the destination.
- Manual-run service boundary: `MailboxRunViewSet.run_now()` accepts the owner and delegates to `start_mailbox_check()`; without local credentials it creates a durable `MailboxCheckRequest` and returns `{queued: true, request_id: ...}`.
- Manual-run UI boundary: `MailboxReview` loads status for the owner but renders the entire `Run check now` section only when `status.has_credentials` is true, making the supported queued deployment path unreachable.

### Hypothesized root cause
The shared message link uses the weaker RFC822 search key instead of the persisted Gmail thread key, while the mailbox page independently mistakes local credentials for permission to show an already-supported deployed run request. · Confidence: high

## Phase 2 — Pattern

This is a capability/display mismatch: backend support exists, but a narrower frontend capability flag hides it. The same class previously occurred in TASK-151 when `can_generate_cv` hid mailbox endpoints on deployment. The direct-link half is an identifier-selection error: a search identifier is used where the model already stores Gmail's direct conversation identifier.

Missing regression tests:
- a URL-builder/serializer test requiring `#all/<thread_id>` when `thread_id` exists;
- a DOM-less server-render test requiring the manual-run button for an owner before status credentials are known or when they are absent.

Similar paths found: every message Gmail action uses `MailboxMessageSerializer.gmail_url`; draft actions use the same builder's separate exact-draft mode and must remain unchanged.

## Phase 3 — Impact

Affected files and callers:
- `backend/jobradar/services/mailbox.py`: single Gmail URL builder.
- `backend/jobradar/serializers.py`: message and draft URL projection.
- `backend/jobradar/tests/test_mailbox.py`: builder contract.
- `backend/jobradar/tests/test_mailbox_panel.py`: API URL contract and existing manual-run owner/queue tests.
- `frontend/src/App.tsx`: all message action links consume `m.gmail_url`; `MailboxReview` owns run-control visibility.
- one focused frontend test for deployed/initial run-control visibility.

The draft URL path must keep using `gmail_message_id` and `#drafts?compose=`. Messages without a stored `thread_id` should retain the RFC822 search fallback rather than lose their only usable link. Owner gating, duplicate-run locking, and no-send behavior remain in existing backend enforcement points.

## Phase 4 — Solution

Minimal fix:
1. Extend the existing builder with an optional `thread_id`; emit the account-scoped `#all/<thread_id>` direct-conversation URL when present, otherwise preserve the RFC822 search fallback. Pass `MailboxMessage.thread_id` from the serializer. Do not add another URL builder.
2. Restore the run-control render gate to `owner` only. Keep status text honest: local credentials run immediately; the deployed path records a request for the cloud check. Export `MailboxReview` solely so the existing DOM-less Vitest setup can pin visibility.
3. Add focused backend and frontend regressions, then run the full backend suite and frontend build/tests.

## Resolution

The shared builder now emits an account-scoped `#all/<thread_id>` URL for persisted Gmail threads, the serializer supplies that id, and the owner-visible run control no longer depends on local credentials.
