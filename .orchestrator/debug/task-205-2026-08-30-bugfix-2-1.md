# Debug session: alternate-port HTTP verification returns 500
Created: 2026-08-30T14:24:30Z
Session: task-205-2026-08-30-bugfix-2

## Phase 1 — Root Cause

### Error

Exact HTTP verification result:

```text
HTTP/1.1 500 Internal Server Error
follow=500 http://127.0.0.1:8010/ title=<title>OperationalError
```

The runserver log reports:

```text
sqlite3.OperationalError: no such table: jobradar_sitedailyusage
...
django.db.utils.OperationalError: no such table: jobradar_sitedailyusage
[2026-08-30 16:23:54,063] ERROR django.server "GET / HTTP/1.1" 500 161637
```

The shell verification command exited 1 after its 302 assertion failed.

### Reproduction

```bash
rm -rf frontend/dist
cd backend
uv run python manage.py runserver 127.0.0.1:8010 --noreload
curl -L http://127.0.0.1:8010/
```

Environment: isolated worktree with no linked owner `.env`, default local SQLite database, alternate port 8010. Frequency: always before migrations are applied.

### Suspect commits

- No product commit: the alternate-port manual verification started a fresh local SQLite database without preparing its schema.
- Existing `UserUsageMiddleware` writes usage rows for `/`; its migration-backed table is required for a full HTTP request.

### Instrumentation data

- `backend/db.sqlite3` existed as a zero-byte file after startup.
- `python manage.py showmigrations --plan` showed every migration as unapplied, including `jobradar.0001_initial` and subsequent jobradar migrations.
- The exception occurs after URL dispatch, inside `UserUsageMiddleware.record_usage()` at `SiteDailyUsage.objects.get_or_create(...)`.
- The production local runtime does not have this condition: it uses the configured remote database, and its existing port-8000 health endpoint is 200.
- No process remained listening on alternate port 8010 after cleanup.

### Hypothesized root cause

The manual HTTP verification used an uninitialized disposable SQLite database, so post-response analytics middleware replaced the redirect with a missing-table 500. · Confidence: high

## Phase 2 — Pattern

This is a verification-environment setup failure, not a routing defect. A full Django request exercises middleware and therefore needs a migrated database even when the target view itself does not query data. The focused RequestFactory resolver test remains the correct database-free unit boundary.

## Phase 3 — Impact

Affected only: the manual alternate-port verification setup and ignored `backend/db.sqlite3` artifact. Production code, migrations, remote data, and the released runtime are unchanged.

## Phase 4 — Solution

Apply existing migrations to the isolated worktree’s disposable SQLite database, rerun the alternate-port server and root/follow checks, then delete the ignored SQLite file. Do not modify middleware or production database behavior for a test-environment mistake.

## Resolution

Applied existing migrations only to the isolated worktree’s disposable SQLite database and reran the alternate-port check. `GET /` returned `302 Found` with `Location: http://localhost:5173`; following it returned HTTP 200 and `<title>DACHApply`. No production database or code was changed. The disposable database was subsequently removed.
