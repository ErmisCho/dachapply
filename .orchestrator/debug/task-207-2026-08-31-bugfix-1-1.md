## Phase 1 — Root Cause

### Suspect commits

- `e6831a9 fix(mailbox): suppress replies after conversation closure` — correctly added `stale_reason`, but its frontend stale branch returns before the existing edit/chat controls.
- `669637f feat(mailbox): ... a conversation with both sides ...` — introduced the `sent_by_owner` display distinction used by the conversation row; app-created draft capture has no separate wire identity.
- `bed69ba feat(mailbox): ... editable drafts` — established the separate draft editor/chat block and owner-scoped endpoints.

### Instrumentation data

1. Persistence boundary: the measured `MailboxDraft.gmail_message_id` exactly matches one captured `MailboxMessage.gmail_id`.
2. Message-model boundary: that matching captured row has `sent_by_owner=True` but no reverse `draft`, because the `MailboxDraft` belongs to the inbound source message, not its later Gmail self-capture.
3. Serializer boundary: `MailboxMessageSerializer` does not expose `gmail_id` or a captured-app-draft discriminator, so the exact identity match is lost before rendering.
4. Conversation UI boundary: `MailboxConversationMessage` derives sender label, alignment, and blue bubble tone solely from `sent_by_owner`, producing `You` plus sent-message styling.
5. Draft-control boundary: `DraftReplyBlock` returns immediately when `draft.stale_reason` is non-empty, so stale drafts cannot reach the already owner-scoped `/edit/` and `/chat/` controls.
6. AI boundary: the existing `/chat/` endpoint is scoped to one exact draft id and includes that draft text server-side, but `draft_chat._build_chat_prompt` supports revision only; an understanding request would be mislabeled as a revision and offered as replacement draft text.

### Hypothesized root cause

The app drops the persisted captured-draft identity at serialization and short-circuits stale drafts before the shared edit/AI controls, so one unsent draft is rendered as sent mail and cannot receive message-specific drafting or understanding help. · Confidence: high

## Phase 2 — Pattern

This is a recurrence of presentation identity being inferred from a broad flag (`sent_by_owner`) after a more specific identity (`MailboxDraft.gmail_message_id == MailboxMessage.gmail_id`) was discarded. The same base conversation row renders all owner captures, so guessing by sender/body would create false positives. The missing regression is a synthetic thread containing received mail, a genuine sent owner reply, and the app draft's Gmail self-capture.

The stale guard is a second instance of a UI status branch replacing capabilities rather than decorating them: stale is advisory context, not a reason the existing owner-scoped edit or local AI endpoints become unsafe.

## Phase 3 — Impact

Affected paths and dependents:

- `backend/jobradar/serializers.py`: message wire shape; inherited by job-mailbox, suggestions, unmatched, and digest serializers.
- `backend/jobradar/views.py`: the job-mailbox action already loads all messages and their drafts and is the narrow place that can build the identity map without N+1 queries.
- `backend/jobradar/services/draft_chat.py`: exact-draft model context and revise-only prompt behavior.
- `frontend/src/types/index.ts`: message/draft chat wire types.
- `frontend/src/App.tsx`: full-conversation row and shared draft editor/AI block.
- Focused backend serializer/view/chat tests and DOM-less frontend render tests.

Normal sent owner mail must remain blue and labeled `You`; current non-stale drafts must keep current editing/revision behavior; blocked drafts remain non-editable; automated tests must fake model/Gmail boundaries.

## Phase 4 — Solution

1. In the owner-scoped job-mailbox response, map each captured Gmail message id to its existing written `MailboxDraft` and serialize it as `app_draft`; do not expose raw Gmail ids and do not query per row.
2. Render an `app_draft` conversation row as an explicit **UNSENT DRAFT**; when stale, add **STALE CONVERSATION REPLY** and the reason, use non-sent styling, omit the reply-to-message action, and put the existing draft controls on that exact row.
3. Keep stale drafts in `DraftReplyBlock`; add the warning above the same edit and AI controls instead of returning early. Avoid duplicate controls by leaving the separate fallback block only when the expanded history has no captured draft row.
4. Extend the existing message-specific AI endpoint with a validated `revise`/`understand` mode. Understanding responses remain non-accepting explanations and never write Gmail; revisions retain guardrails and explicit acceptance.
5. Add synthetic regressions for discriminator ownership, no N+1 behavior, stale editing controls, sent-message preservation, exact-draft AI prompts, and non-writing understanding responses.

## Resolution

Implemented the persisted-id `app_draft` mapping, inline unsent/stale presentation, preserved edit controls, and explicit revise/understand AI modes. Added synthetic backend/frontend regressions. Verification: 1,040 backend tests, 198 frontend tests, production build, checks, migration check, audit, no-send/delete scan, synthetic browser interaction, and read-only measured-case serialization all passed.
