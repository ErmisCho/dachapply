# Debug session: focused local-root test requires database access
Created: 2026-08-30T14:14:10Z
Session: task-205-2026-08-30-bugfix-1

## Phase 1 — Root Cause

### Error

Exact focused-test failure:

```text
______ test_local_root_redirects_to_vite_when_frontend_build_is_missing _______
response = Client().get('/')
RuntimeError: Database access not allowed, use the "django_db" mark, or the "db" or "transactional_db" fixtures to enable it.
1 failed, 4 passed, 1 warning in 1.45s
```

Command exit code: 1.

### Reproduction

```bash
cd backend
uv run pytest -q jobradar/tests/test_settings.py jobradar/tests/test_local_runtime_launcher.py
```

Environment: Windows, CPython 3.13.5, pytest-django, test settings with in-memory SQLite. Frequency: always for an unmarked test using Django `Client().get('/')`.

### Suspect commits

- Current uncommitted test addition in `backend/jobradar/tests/test_settings.py` — it uses the full Django client for a URL resolver assertion.
- No production commit is implicated; the redirect URLconf itself was reached before middleware performed the database write.

### Instrumentation data

- Stack boundary, test → Django handler: `Client().get('/')` executes the complete middleware chain.
- Boundary, response → usage middleware: `UserUsageMiddleware.__call__` calls `record_usage()` for `/` after obtaining the redirect response.
- Boundary, usage middleware → database: `SiteDailyUsage.objects.get_or_create(...)` requests a cursor.
- pytest-django blocks that cursor because the focused routing test did not request `db`.
- The test needs to prove URL resolution and the RedirectView response only; usage analytics/database behavior is unrelated.
- Existing tests use `RequestFactory` when direct view execution is the intended boundary.

### Hypothesized root cause

The routing-only regression test used Django’s full HTTP client, which invoked database-writing analytics middleware unrelated to the behavior under test. · Confidence: high

## Phase 2 — Pattern

This is an over-broad test boundary. Adding `db` would make the test pass but would hide the mismatch and make a URLconf test slower. Resolving the URL and invoking its callback with `RequestFactory` tests the exact layer that changed and avoids middleware entirely.

## Phase 3 — Impact

Affected only: `backend/jobradar/tests/test_settings.py` test imports and request invocation. Production code is unaffected. The test’s URLconf reload/restore remains necessary to exercise an explicitly absent frontend build without leaking module state to sibling tests.

## Phase 4 — Solution

Replace `Client` with `RequestFactory` and use `django.urls.resolve(..., urlconf=config.urls)` to invoke the matched redirect callbacks directly for `/` and `/admin`. Keep the same status/location assertions and URLconf restoration.

## Resolution

Replaced the full Django client with `RequestFactory` plus direct URL resolution, keeping the test at the changed routing boundary and avoiding unrelated analytics middleware. The focused pair passed: 5 tests in 0.30s; the full backend suite later passed 1028 tests.
