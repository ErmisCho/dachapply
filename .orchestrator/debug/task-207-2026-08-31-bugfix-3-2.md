# Debug session: concurrent fetch remote-ref compare-and-swap
Created: 2026-08-31T14:02:00Z
Session: task-207-2026-08-31-bugfix-3

## Phase 1 — Root Cause

### Error

```text
error: cannot lock ref 'refs/remotes/origin/main': is at 5f8055f... but expected 6a17c8a...
! 6a17c8a..5f8055f main -> origin/main (unable to update local ref)
exit code 1
```

### Reproduction

Run two `git fetch origin main` commands concurrently from worktrees sharing one repository object store immediately after main advances. Frequency: 1/1 in this parallel call.

### Suspect commits

None; repository coordination timing only.

### Instrumentation data

The root checkout's parallel fetch successfully advanced the shared `origin/main` ref from `6a17c8a` to `5f8055f`. The worktree fetch started from the old expected value and then failed its compare-and-swap because the first fetch had already written the desired new value.

### Hypothesized root cause

Two parallel fetches raced to update the same shared remote-tracking ref, and the losing fetch correctly refused its stale expected value even though the winning fetch had already installed the target SHA. · Confidence: high

## Phase 2 — Pattern

Git worktrees share refs; fetches against the same remote must be serialized when their result updates the same remote-tracking branch.

## Phase 3 — Impact

No commit or working-tree content was lost. Shared `origin/main` already equals the desired merge SHA.

## Phase 4 — Solution

Verify `origin/main` directly and avoid parallel fetches within one repository for subsequent close-out operations.

## Resolution

Verified shared `origin/main` at `5f8055fb1c305f01396756f07795ddb22f83591a`; no corrective mutation was needed.
