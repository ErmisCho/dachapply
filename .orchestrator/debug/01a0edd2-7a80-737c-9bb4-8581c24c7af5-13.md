# Debug session: Live replica assertion exits after successful Azure update
Created: 2026-10-01T12:58:00Z
Session: 01a0edd2-7a80-737c-9bb4-8581c24c7af5

## Phase 1 — Root Cause

### Error

GitHub Actions run `36864599690`, job `110378150578`, step `Deploy image to Azure Container Apps`:

```text
2026-10-01T12:57:25.3607748Z ##[error]Process completed with exit code 1.
```

The preceding `az containerapp update --min-replicas 0 --max-replicas 1 --output none` completed. The step then executed:

```bash
read -r MIN_REPLICAS MAX_REPLICAS <<< "$(az containerapp show ... --query '[properties.template.scale.minReplicas, properties.template.scale.maxReplicas]' -o tsv)"
test "$MIN_REPLICAS" = 0
test "$MAX_REPLICAS" = 1
```

### Reproduction

Exact output-shape reproduction with the installed Azure CLI:

```bash
output=$(az version --query '[`0`, `1`]' -o tsv)
read -r A B <<< "$output"
printf 'raw=%q A=%q B=%q\n' "$output" "$A" "$B"
test "$B" = 1
```

Observed:

```text
raw=$'0\r\n1' A=$'0\r' B=''
exit=1
```

Environment: Azure CLI on Windows for the local shape probe; GitHub-hosted Ubuntu runner for the failing deployment. Frequency: always for a two-element primitive array rendered by Azure CLI TSV.

### Suspect commits

- `a3e7fc6` / PR #196 — introduced the live assertion.
- `cca5c4e` / PR #195 — introduced the correct zero-to-one update and deployed successfully.

### Instrumentation data

- Azure CLI TSV renders a primitive array vertically: `0\n1\n`, not `0<TAB>1\n`.
- Bash `read` consumes one line. It therefore assigns `MIN_REPLICAS=0` and leaves `MAX_REPLICAS` empty.
- With `bash -e`, `test "$MAX_REPLICAS" = 1` exits the deployment step with status 1.
- The Azure update itself completed before the assertion, so the failure is in verification parsing, not in applying the requested scale range.

### Hypothesized root cause

The deployment verifier assumes Azure CLI TSV emits the two queried array values on one tab-separated line, but it emits one value per line and Bash `read` discards the second line. · Confidence: high

## Phase 2 — Pattern

This is an output-shape mismatch at a CLI/shell boundary. No similar `read -r ... <<< "$(az ... -o tsv)"` pattern exists elsewhere in `.github/` or `scripts/`. The missing check was a fixture proving the actual two-line Azure CLI TSV shape before merging the shell parser.

## Phase 3 — Impact

Affected file: `.github/workflows/deploy-container-apps.yml`. The bad parser runs only after a successful production update. It prevents the public health step and marks deployments failed, but does not revert or alter the already-applied zero-to-one range.

## Phase 4 — Solution

Query each scalar independently so no collection formatting or shell splitting is involved: assign `MIN_REPLICAS` and `MAX_REPLICAS` from separate `az containerapp show --query properties.template.scale.<field> -o tsv` calls, then retain the exact assertions and logged range. Verify the shell shape locally and through a fresh authenticated main deployment.

## Resolution

TASK-257 follow-up changes `.github/workflows/deploy-container-apps.yml` to query each scale field as a scalar before asserting. The local Azure CLI shape probe now reports `0..1`; final verification is a fresh authenticated main deployment that must print `Replica range: 0..1` and pass public health.
